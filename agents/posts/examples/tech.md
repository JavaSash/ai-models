👨‍💻Как двигаются данные в боте (data stream)

Пользователь пишет боту, бот отвечает. Звучит просто, но под капотом данные совершают целое путешествие по моему приложению, распадаются на байты и снова собираются в понятные пользователю слова.

Общий поток данных такой:

Пользователь → Telegram → Адаптер → [Событие] → [Стратегия] → [Бизнес-логика] → Ответ

Разложу по шагам

1️⃣ Пользователь отправляет сообщение или нажимает кнопку

2️⃣ ApplicationListener получает апдейт от Telegram

3️⃣ На основе апдейта создаётся событие:
- TgReceivedMessageEvent - обычное сообщение
- TgReceivedCallbackEvent - нажатие кнопки
- TgStepMessageEvent - сообщение внутри шага диалога

4️⃣ Через ApplicationEventPublisher (Spring) событие публикуется внутри приложения

5️⃣ Listener ловит событие и передаёт его дальше

6️⃣ По step_code из БД определяется текущий шаг пользователя

7️⃣ Выбирается соответствующая стратегия, которая выполняет нужную логику обработки шага

8️⃣ Ответ отправляется пользователю через TelegramConsumer

Упрощённо схема такая:

📬 Telegram даёт апдейт
📧 приложение превращает его в событие
🗳 стратегия решает что делать дальше

Но в целом, да: 
пользователь написал → бот ответил 🤖

👨‍💻Отчёты за период без копипасты

Когда добавлял отчёты📊 (сегодня/неделя/месяц/год), сразу старался унифицировать этот функционал. Вместо 4х одинаковых кусков кода - 1 метод с параметрами периода отчёта:
fun reportForPeriod(
        userId: String,
        from: Instant,
        to: Instant,
        label: String
    ): PeriodReport 

Всё остальное - просто игрушки подготовка дат:
- today → now → now+1 day
- week → начало недели → now
- month → 1 число → now
- year → начало года → now

В адаптере та же история.

Сделал абстрактный ReportRepository, где:
- общая логика получения данных
- обработка ошибок
- маппинг
- fallback на stub
Конкретный временной отчёт просто реализовывает метод поставки данных
class ReportTodayRepository : ReportRepository() {
    override fun getPeriodReport(chatId: String) =
        reportClient.getTodayReport(chatId)
}

Кайф, когда в работе абстракции упрощают жизнь, а не усложняют её💡

👨‍💻Обработка ошибок через Step класс

Когда я получше разобрался в работе адаптера, смог оценить качество его архитектуры🏗. И даже начал мыслить в её рамках👨🏻‍🔬. 

Поэтому обработку ошибок я уже видел как отдельный Step класс:
1. Возникает ошибка
2. Приложение её ловит и переходит на ErrorStep, запоминая шаг возникновения ошибки
3. Выдаёт текст ошибки пользователю и возвращается на шаг, где она возникла

ИИ предлагал всякие сомнительные реализации обработки ошибок⚠️, так что я остался при своём. 

Моё решение вписывается в текущую архитектуру, не ломает диалог, поддерживает fallback и легко масштабируется. Я уже легко добавил обработку ошибок в другие шаги.

👨‍💻Про finite state machine

Сервис-адаптер – это finite state machine. Я не сталкивался раньше с FSM, так что разбирался с ним отдельно. Это модель с фиксированными состояниями и переходами между ними по событиям, в моменте она может находиться только в одном из состояний🌀. 

Такой подход отлично ложится во взаимодействие пользователя с Telegram-ботом🤖. В отличие от REST, пользователь вводит данные последовательно, и система должна помнить контекст диалога💬. 

Каждый шаг (Step-класс) определяет следующий, а состояние пользователя хранится в базе (таблицах контекста диалога). Это позволяет реализовывать сложные сценарии📃 (создание транзакции, поиск по фильтрам) без парсинга одного длинного сообщения.

👨‍💻 n8n vs своя архитектура бота

Недавно коллега рассказал про n8n (https://n8n.io/) - open-source платформу для автоматизации, где можно собирать бизнес-логику из блоков (нод) почти без кода. По сути low-code оркестратор: API, базы, вебхуки, cron, интеграции - всё связывается визуально.

Идея показалась интересной. Даже думал собрать Wimme там. На первый взгляд для MVP выглядит сильно:
✅ быстро поднять прототип
✅ не писать обвязку для интеграций
✅ визуально видно весь flow
✅ легко тестировать гипотезы
✅ низкий порог входа

Для простого Telegram-бота формата:
"получил сообщение → распарсил → записал в БД → ответил" - хороший вариант. Но у меня бот - не просто набор действий. Там stateful-диалоги, разные флоу, черновики транзакций, контекст поиска, ошибки на шагах, повторный ввод, FSM, бизнес-правила, отчёты, агрегации.
И вот тут low-code уже не подходит как решение.
Если в коде сложная логика — это просто:
if / when / strategy / template method
то в n8n это быстро превращается в:
🫠 15 нод
🫠 ветвления
🫠 кастомные JS-вставки
🫠 ручное протаскивание контекста между шагами

А это уже тот же код, только в множестве коробок.

Мои аргументы за свою архитектуру:
- код хранится в VCS
- полный контроль над доменной моделью
- проще рефакторить
- проще тестировать
- проще масштабироваться

В итоге вывод для себя такой:
n8n - отличный инструмент для automation-first продуктов.
Но если у тебя logic-first продукт, где ядро - это бизнес-логика и сложные сценарии, код всё ещё выигрывает.
